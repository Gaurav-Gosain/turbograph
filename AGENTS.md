# AGENTS.md — правила работы агента над этим проектом

## Роль и самостоятельность
Ты — coding-агент, который правит существующий код (Go, Clean Architecture, SQLite).
Работай самостоятельно: читай код, запускай тесты/сборку, ищи причину, предлагай минимальный патч.
Не жди пошаговых инструкций на каждую мелочь. Исследуй сам (код, тесты, документацию в репо, при необходимости — web/search и MCP).

По **ключевым** вопросам всегда спрашивай пользователя перед действием:
- смена публичных API / сигнатур usecase/ports;
- миграции схемы БД или изменение существующих миграций;
- изменение поведения, которое может ломать обратную совместимость CLI;
- добавление новых зависимостей;
- любой git commit / push / force / rewrite history;
- удаление файлов или большие рефакторинги «заодно».

Если сомневаешься, «ключевой ли это вопрос» — спроси коротко.

## Git и коммиты
- **Никогда** не делай `git commit`, `git push`, `git rebase`, `git reset --hard` и подобные операции без **явного** разрешения пользователя в текущем сообщении.
- Можно смотреть статус, diff, log — это нормально.
- Предлагай текст коммита и список файлов, но не коммить сам.

## Инструменты и MCP
Когда нужно — активно используй доступные инструменты:
- файловая система, shell (`go build`, `go test`, `go vet`, `golangci-lint` и т.д.);
- поиск по коду, чтение файлов;
- **Go MCP / LSP плагины** (включать при работе с этим проектом):
  - `gopls` — навигация, find references, hover, diagnostics, rename;
  - `godoc-mcp` — документация пакетов и символов;
  - `gograph-mcp` — зависимости и структура пакетов;
  - `go-dev-mcp` — вспомогательные Go-операции разработки.
  Если плагин выключен, а он нужен для задачи — сначала включи его (или попроси пользователя), затем используй.
- другие MCP (браузер, поиск и т.п.) — по делу, не «для галочки».

Не выдумывай результат команды или диагностики: запускай инструмент и смотри реальный вывод.

## Архитектура (не нарушать)
Минимальные точечные правки. Не переписывай файлы целиком, если хватает локального изменения.
Не меняй форматирование и комментарии, не относящиеся к задаче.
Язык: идентификаторы на английском, комментарии — как в существующей базе (русский).

## Качество после каждого изменения
После любого функционального изменения код обязан:
1. Собираться: `go build ./...`
2. Проходить: `go vet ./...`
3. Проходить: `golangci-lint run ./...` (если установлен)
4. Проходить существующие и новые тесты: `go test ./...` (и `-race` когда уместно)

Каждый функциональный пункт закрывай тестом, который падал бы на старом коде и проходит на новом.
Не удаляй и не ослабляй существующие проверки ради «зелёных» тестов.

## Порядок работы
1. Сначала баги / критичные исправления.
2. Потом новая функциональность по ТЗ.
3. Потом документация и мелкие улучшения.
Делай изменения логическими порциями (по пунктам), а не одним огромным диффом.
Не трогай файлы документации ТЗ (TZ/*.md), кроме явно указанных (например docs/README.md при изменении команд).

## Исследования
Если не хватает контекста:
- читай соседний код и тесты;
- смотри существующие паттерны (merge при Update, проверка ролей, ошибки domain.* и т.д.);
- используй gopls / godoc-mcp / gograph-mcp;
- при необходимости ищи в сети (Go docs, best practices, аналогичные паттерны).
Не придумывай API, которых нет в проекте.

## Коммуникация
- Кратко объясняй, что сделал и почему.
- Показывай команды, которые запускал, и их результат, если это важно.
- Если задача противоречива или неясна — спроси, а не угадывай.
- Не обещай то, чего не можешь проверить.

## Чего не делать
- Не коммитить без явного разрешения.
- Не ломать слои архитектуры.
- Не добавлять «на всякий случай» большой рефакторинг.
- Не оставлять мёртвый/недоделанный код.
- Не менять поведение ради удобства тестов, если это не согласовано.
